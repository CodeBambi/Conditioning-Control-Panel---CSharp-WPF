# Greenfield Client Workflow Prompt

Use this prompt to coordinate work on the greenfield Windows/Linux Avalonia client in `client/`.
It is intentionally independent of any particular command-line tool, model, workflow engine, or
historical task archive.

## Start With Reconciliation

Before planning, editing, or delegating, inspect the current repository state:

1. Read `docs/constitution.md`, `client/docs/port-workflow.md`, the relevant client contracts, and
  `client/docs/task-board.md`.
2. Inspect `git status`, recent relevant history, active worktrees or workspaces, and any scoped
  uncommitted changes. Preserve work whose owner or purpose is not yet clear.
3. Identify the next unblocked board row, its dependencies, the governing behavior evidence, and
  the exact verification it requires.
4. Repair a stale authoritative document before relying on it. The task board is the only live
  queue; old logs, summaries, and workflow state are evidence only.

Report the recovered state and choose one coherent next action: resume isolated work, review an
existing change, implement one bounded row, or mark the work blocked with its exact missing
evidence or owner decision.

## Product Rules

- Build the new product only under `client/`. The WPF product is read-only behavioral evidence;
  preserve user-observable outcomes, never its implementation architecture.
- Treat the port as a contract of visible behavior, not a code migration: the authoritative question
  is how the user interacts with the feature and what is visible on screen, not how the WPF app
  happened to be structured internally.
- Research current official Avalonia documentation before selecting a v12 API, dependency, native
  integration, platform behavior, or rendering approach.
- A Windows build, stub, no-op fallback, or markup alone does not prove Windows and Linux support.
  Record the exact unavailable platform gate when evidence cannot yet be obtained.
- Do not broaden webcam, biometric, secret, path, logging, capture, moderation, consent, or
  network boundaries without an owner decision.
- The product must stay LIGHT AT MAXIMUM SETTINGS, not merely at defaults. A session with every
  effect enabled at its highest values - video on every monitor, spiral, tint, flashes, subliminals,
  animated GIFs, bubbles, moving text - is the performance contract, and it is the configuration to
  measure. A cost that is invisible at defaults and unusable at maximum is a defect, not a tuning
  preference.
- Optimization claims require a MEASUREMENT, before and after, taken on the running product at
  maximum settings. Frame cadence, CPU, GPU, memory, allocation rate, and native window/surface
  count are the units. A reasoned argument, a green build, or a lower number in a micro-benchmark
  does not discharge a performance claim.
- Reducing the number of native surfaces must never silently change an effect's INPUT POLICY.
  Which layers pass clicks through to the desktop and which capture them is a per-effect product
  contract, and any grouping that merges layers must preserve each one's documented policy, z-order,
  capture visibility, and monitor scope.
- Use deterministic test synchronization. Do not introduce wall-clock waits or process-wide
  `CCP_DATA_ROOT`; set an isolated data root only for the individual operation that needs it.
- The active workflow harness is not frozen. While porting to Avalonia it must keep working on the
  task, learn from each verified result, and improve the current harness by creating or revising the
  reusable skills, agents, role definitions, templates, or checks it needs. Reuse older proven
  workflow assets when they still match the contract, and do not keep dead historical workflow state
  that no longer helps the active work.

## Workflow Roles And Isolation

A compatible workflow harness may use any combination of generic roles:

- A coordinator reconciles state, owns shared documents and shared merge points, and keeps scope
  aligned with the task board.
- A worker owns one bounded change in an isolated workspace or worktree.
- A researcher gathers WPF behavior and current primary-source platform evidence without changing
  product code.
- An independent reviewer evaluates a completed change against its contract and evidence without
  relying on the producing context.

No fixed number of workflows or workers is authorized or required. Launch as many concurrent,
isolated workflows as current capacity safely supports only when every active change has disjoint
file scope, a single explicit owner for each shared chokepoint, and enough CPU, memory, disk, and
provider capacity. Build and test concurrency remains separately limited through
`client/tools/gate/with-slot.mjs`.

## Implement, Review, And Verify

Keep each change to one coherent board outcome. Before completion:

1. Verify the relevant WPF behavior and current platform facts.
2. Run focused checks while implementing, then the task's mechanical verification.
3. Use a fresh independent review for architecture, dependencies, platform seams, privacy,
  security, lifecycle, or other high-risk changes.
4. Obtain headed evidence for visual, input, windowing, media, scaling, occlusion, or composition
  claims. A headless result does not discharge a presentation claim.
5. Update the matching task-board row with concise evidence or the exact blocker.

The standard client checks are:

```powershell
node client/tests/floor/check-warnings.mjs
node client/tests/floor/check-floor.mjs
```

Use `--cold` with the warning gate after project, build-property, target, or lock-file changes.
The floor's exact count changes only with its corresponding test change and a concise reason in
`client/tests/floor/floor.json`.

When verified port lessons reveal a recurring coordination or technical problem, create or revise
the reusable workflow assets available in the current harness, such as instructions, skills, role
definitions, templates, or checks. Keep them evidence-based, narrowly scoped, and independent of a
named vendor or model; do not add automation merely to preserve a historical process.

Stop and seek an owner decision when evidence conflicts, a required platform gate is unavailable,
verification fails repeatedly for the same cause, scope must expand beyond the board row, or a
safety/privacy decision is unresolved. Do not substitute workflow output, consensus, or a green
compile for product evidence.
