# Client architecture

## Scope

- Greenfield Avalonia desktop application.
- Windows and Linux only.
- All product code lives under `client/`.
- WPF supplies behavioral evidence only.
- The first Avalonia attempt supplies lessons only.

## Decisions

### A-001: Unified composition domain for overlapping real-time visuals

- **Problem and current need:** CCP can display video, flashes, subliminals, tint, spiral, blur, moving text, bubbles, and other effects concurrently. Independent effect windows make ordering, frame presentation, focus, click-through, capture behavior, and multi-monitor lifecycle interact at the OS-window level. The new client needs one coherent rule before feature contracts are implemented.
- **Considered alternatives:**
	1. one native window and bitmap presentation path per effect, following WPF;
	2. one shared composition domain for overlapping passive and real-time visuals, with separate windows only where user-observable behavior requires them;
	3. decide independently for every effect with no shared default.
- **Selected direction:** Use a shared composition domain with explicit visual ordering as the default for overlapping passive and real-time effects. This is a product-level direction, not approval of the first attempt's compositor classes, layer interfaces, frame timer, Skia APIs, or fixed z values. Interactive dialogs and surfaces may remain separate windows when focus, accessibility, native controls, capture policy, or input behavior requires that boundary.
- **Windows impact:** The composed host must preserve each documented effect's topmost, focus, click-through, capture, and monitor behavior. Regions intended to be passive must not block desktop input. Any interactive region must handle the event without unintentionally forwarding the same click to the application beneath it. Windows-only capture exclusion may require more than one host because affinity is applied at window scope; this must be decided from feature contracts rather than copied from the first attempt.
- **Linux impact:** The same composition and ordering outcome is required. Linux acceptance cannot be claimed until topmost, transparency, click-through, interactive-region input, and multi-monitor behavior are proven on the supported display backends. If equivalent behavior is unavailable, the exact gap requires a product decision; a silent no-op is not support.
- **Evidence and sources:** The accepted lesson and narrow code citations are recorded in [`first-attempt-lessons.md`](first-attempt-lessons.md#unified-composition-for-real-time-visuals). Current Avalonia 12.1 API evidence confirms custom drawing and explicit repaint invalidation remain available, while the direct Skia lease API is marked unstable: [ICustomDrawOperation](https://api-docs.avaloniaui.net/docs/T_Avalonia_Rendering_SceneGraph_ICustomDrawOperation), [InvalidateVisual](https://api-docs.avaloniaui.net/docs/M_Avalonia_Visual_InvalidateVisual), and [ISkiaSharpApiLeaseFeature](https://api-docs.avaloniaui.net/docs/T_Avalonia_Skia_ISkiaSharpApiLeaseFeature).
- **Consequences:** Feature contracts must state visual ordering, interaction regions, capture visibility, and monitor scope so the composition design can satisfy observable behavior. New per-effect windows require an explicit reason. Rendering API and package selection is deferred until a vertical slice validates current Avalonia v12 behavior on both target platforms.
	- Shared composition must not imply shared ownership of effect state. Video lifecycle events cannot silently overwrite tint intensity. The rendered color overlay must never reach 100-percent opacity, regardless of pulses, ramps, commands, overlapping requests, media state, or failures. Temporary tint changes require a safety ceiling below full opacity and deterministic restoration to the latest valid underlying value after overlap, cancellation, playback error, or teardown. See [`first-attempt-lessons.md`](first-attempt-lessons.md#color-overlay-must-never-become-fully-opaque).
	- The first slice must verify actual rendered tint during web and mandatory video playback, including abnormal termination; checking only the persisted opacity setting is insufficient.
- **Unresolved questions:**
	- Which first vertical slice best validates simultaneous media, overlay ordering, transparency, and input?
	- Which Linux display backends are release requirements?
	- Which effects must appear in screen capture, and which must be excluded?
	- Which composed effects contain interactive regions, and should handled pointer events be swallowed?

### A-002: Preserve DTRH as a hosted web product

- **Problem and current need:** The current Down the Rabbit Hole experience is a complete offline web roguelike. Rebuilding its Three.js/WebGL engine as native Avalonia code would duplicate a working product, create two games to maintain, and contradict the requirement to keep only the new web version. The desktop client still must supply persistence, progression, media, audio/video, windowing, and failure recovery on Windows and Linux.
- **Considered alternatives:**
	1. port or retain the classic/native DTRH implementation;
	2. rewrite the web game into Avalonia controls or a custom renderer;
	3. copy the web payload and build the smallest cross-platform host around its existing protocol.
- **Selected direction:** Select option 3. `ConditioningControlPanel/Resources/web/dtrh/` is the behavioral source payload and should be copied as a unit into the client. The new client has one DTRH implementation and no classic fallback. DTRH runs in a dedicated opaque, focusable, non-topmost window because it is an interactive application, not a passive overlay. Host logic owns save slots, settings validation, native effects, progression, filesystem integration, watchdogs, and the version-1 message protocol described in [`capability-inventory.md`](capability-inventory.md#down-the-rabbit-hole).
- **Browser direction:** The current official candidate is [`Avalonia.Controls.WebView`](https://www.nuget.org/packages/Avalonia.Controls.WebView/12.0.1) `12.0.1`, restored and runtime-tested against the client's Avalonia `12.1.x` baseline before admission. Its `NativeWebView` uses WebView2 on Windows and WPE WebKit offscreen rendering on Linux; official documentation states that Linux works on X11 and Wayland and documents WebKitGTK/`NativeWebDialog` fallbacks. The package is .NET 8+, MIT licensed, and maintained in the official [`AvaloniaUI/Avalonia.Controls.WebView`](https://github.com/AvaloniaUI/Avalonia.Controls.WebView) repository. Sources: [NativeWebView](https://docs.avaloniaui.net/controls/web/nativewebview), [embedding web content](https://docs.avaloniaui.net/docs/app-development/embedding-web-content), and [environment options](https://docs.avaloniaui.net/controls/web/webview-environment).
- **Portable host shape:** Prefer a loopback HTTP origin owned by the application over emulating WebView2 virtual-host mappings. One loopback server can preserve the payload's `/dtrh/...` root-relative URLs and serve isolated routes for game files, user assets, bundled art, Loom files, and active-mod DTRH files on both platforms. It must bind loopback only, use an unpredictable per-process capability or equivalent route protection, canonicalize every path beneath an allowlisted root, return correct MIME/range/cache/CORS headers, and stop with the game/application. This is a candidate, not an approved implementation, until the spike proves workers, seeking, WebGL uploads, and throughput.
- **Bridge constraint:** The copied `bridge.js` expects `window.chrome.webview.postMessage` and WebView2-style message events. `NativeWebView` documents the portable page-to-host call as `invokeCSharpAction(body)` and host-to-page execution through `InvokeScript`. The public API found in current documentation does not expose a cross-platform document-created-script hook. Therefore byte-for-byte payload compatibility is `UNPROVEN` on Linux. The spike must first try an unchanged payload. If that cannot work without platform-specific native injection, approve one minimal transport-only edit to `bridge.js` that selects WebView2 when present and otherwise uses the portable Avalonia bridge, while preserving buffering, protocol version 1, message objects, and every game module unchanged. Do not build a large compatibility framework merely to preserve one file byte-for-byte.
- **Resource constraint:** `WebResourceRequested` exposes request data and mutable headers, not a documented portable response-body replacement API. WebView2's virtual-host mapping exists in Windows-specific internals only. Do not assume either mechanism can serve the payload on WPE. The loopback-origin spike is the default feasibility test.
- **Windows impact:** Use the official WebView's WebView2 backend. Verify the package baseline, autoplay configuration, WebGL, bridge ordering, loopback origins, CORS-clean texture/media upload, focus, fullscreen, browser failure reporting, and packaged deployment. Do not inherit the first attempt's Windows-only `WebView2BrowserHost` as the cross-platform contract.
- **Linux impact:** Install/package the documented WPE runtime dependencies and test `NativeWebView` under both X11 and Wayland. Current WPE `Auto` rendering maps to shared-memory software presentation; EGL and DMA-BUF modes are not implemented, so acceptable game performance and WebGL capability must be measured. WebKitGTK or `NativeWebDialog` is an explicit fallback candidate only if it passes the same dedicated-window, protocol, WebGL, media, and focus contract. Opening an external browser is not equivalent.
- **Failure behavior:** Boot failure, missing runtime dependencies, protocol mismatch, or repeated browser failure closes DTRH and presents an actionable error. The new client never launches a classic game. Stale fallback wording inside the copied page is a small payload-maintenance issue, not permission to restore the old mode.
- **Consequences:** No DTRH game-engine optimization is planned. Native work is limited to the host obligations required by the existing page. Package admission and the final bridge/origin mechanism remain blocked on a Windows/Linux runtime spike. DTRH cannot be marked supported from compilation or a successful navigation alone.
- **Acceptance:** The spike must exercise the exact copied page, `ready`/`init`/`manifest` ordering, one message in each direction, modules/import maps, module workers, WebGL, WebAudio/autoplay, video load/seek, user-media texture upload, bundled art, Loom read/write, fullscreen round-trip, graceful exit, and an injected boot/process failure on Windows, Linux X11, and Linux Wayland. Record browser/runtime versions and measured startup/frame behavior.

### A-003: Native single-decode presentation for all fullscreen video

- **Problem and current need:** Mandatory video worked well through native decoding and shared composition. Fullscreen browser video and browser screen-capture mirroring were unreliable, introduced another rendering lifecycle, distorted differently shaped displays, and could not guarantee synchronization or Linux support. The product requires the same video on every monitor while retaining the successful Skia/UCE visual levels.
- **Considered alternatives:**
	1. keep the browser fullscreen on one monitor and capture/stretch it to the others;
	2. launch one native player or decoder per monitor;
	3. use one native decoder/timeline and present its shared frame through the composition domain on every monitor.
- **Selected direction:** Select option 3 for mandatory, local, direct-URL, and supported online sources. Browser fullscreen and browser-capture mirroring are not playback fallbacks. The browser may participate only in source discovery, authorization, or controls needed to obtain a native-decodable source. Mandatory behavior becomes policy on top of the same renderer rather than a separate implementation.
- **Composition contract:** Preserve the successful UCE ordering concept. Video is the bottom content level. Each monitor receives the same frame identity, aspect-fitted and centered in that monitor's physical target. Opaque black fills uncovered regions in the video level. Spiral and the bounded color overlay remain above both frame and bars; established higher levels retain their relative order. This naturally produces black bars tinted by the active overlay and crossed by the spiral without coupling video state to overlay state.
- **Display contract:** Enumerate all monitors and use their individual OS-reported physical bounds, scaling, and orientation. Support negative coordinates, vertical arrangements, gaps, mixed DPI/resolution, portrait, and flipped orientations. Do not manually rotate solely from an orientation label when the platform has already transformed the desktop; prove the required transform per backend. React to live display changes without restarting playback or leaving stale surfaces.
- **Synchronization and resources:** Decode once, produce one playback clock and one audible stream, and fan the shared presented frame to every per-monitor composition target. Independent players are rejected even if their start times are close. Monitor count must not multiply decoders, audio sessions, network downloads, or frame storage.
- **Online-source boundary:** A direct media URL or supported manifest can use native playback. Arbitrary HTML pages, browser-local `blob:` URLs, Media Source Extensions, cookies/headers, expiring links, and DRM may not be transferable. The client will not bypass DRM and will not claim universal site extraction. A source-handoff spike and explicit supported-source matrix are required. Unsupported sources fail visibly rather than reverting to browser fullscreen/capture.
- **Windows impact:** Prove the one-decoder path across arbitrary Windows display topology and all orientations reported by the backend. Validate direct files and approved online source forms, one audio session, display hot-plug/reorientation, UCE ordering, and teardown.
- **Linux impact:** Provide the same result under supported X11 and Wayland sessions. Missing source extraction, decoder protocol/codec support, orientation reporting, or composition behavior is a surfaced capability failure, not a no-op or browser fallback.
- **Safety and privacy:** Frames remain memory-only. Do not log signed URLs, cookies, authorization headers, DRM data, or page content. Video lifecycle never mutates persistent overlay intensity, and actual rendered tint stays below full opacity across the frame and bars.
- **Acceptance:** The contract and evidence are detailed in [`capability-inventory.md`](capability-inventory.md#video-presentation). A frame-numbered test must prove the same presented frame on all monitors; a composition capture must prove video/black below spiral and tint; instrumentation must prove one decoder, one timeline, one network source, and one audio output regardless of monitor count.

### A-004: Stable feature identities and one quick-toggle command path

- **Problem and current need:** Some first-attempt dashboard cards do not quick-toggle. The card raises a routed request, but dispatch compares localized title strings, and cards with test capability replace plain right-click with a context menu. Both make interaction depend on presentation rather than feature identity.
- **Selected direction:** Every dashboard card carries a stable feature identifier. Left-click, plain right-click, popup toggles, keyboard/accessibility actions, automation, and settings changes converge on one feature command path that validates locks, changes the setting, applies the live service transition, persists, and updates observable card state. Display titles and themes never participate in dispatch.
- **Exceptions:** `Visuals` and `System` have no aggregate command. Locked cards reject toggles. Help and test actions are separate commands and cannot consume plain right-click.
- **Consequences:** Do not duplicate per-feature start/stop switch statements across card and popup code. The smallest shared command registry or existing view-model command surface that provides one authority is preferred; no speculative framework is required.
- **Acceptance:** The dashboard contract in [`capability-inventory.md`](capability-inventory.md#dashboard-and-feature-popups) passes for all cards, languages, themes, stopped state, and running sessions on Windows and Linux.

### A-005: Window semantics precede shared chrome

- **Problem and current need:** The first attempt contains many visually similar Avalonia windows, but owner feedback reports that they look and behave unlike WPF. Similar chrome does not mean equivalent modality, ownership, activation, focus, taskbar, topmost, resize, placement, or lifetime.
- **Selected direction:** Build and review a per-window behavioral manifest from WPF before implementing a shared window shell. Reusable theme resources and chrome controls are allowed only after each window retains its own semantic classification and property/lifecycle contract.
- **Consequences:** There is no global "make every popup borderless", "make every child modal", or "make every secondary window topmost" rule. Modeless feature settings, editors, consent dialogs, notifications, overlays, AvatarTube, and standalone applications remain distinct. Platform limitations are recorded per behavior and backend.
- **Acceptance:** Every retained window passes the manifest evidence in [`capability-inventory.md`](capability-inventory.md#desktop-window-behavior) on Windows and supported Linux environments. Visual similarity alone is insufficient.

### A-006: Avatar animation is validated at the rendered frame

- **Problem and current need:** The first attempt contains timers, GIF decoders, invalidation calls, and emote engines, yet the owner observes no working AvatarTube animation. Code-path activity does not prove visible animation. Initialization also differs from WPF: the first-attempt constructor creates the pose timer without starting it for the initial static set and detects an animated GIF without unconditionally loading it before later mode selection.
- **Selected direction:** Preserve the WPF animation outcomes, not its animation library. Static pose fades, looping animated assets, speech/emote sequencing, A/B crossfades, and gentle float are separate modes coordinated by one visible-avatar lifecycle. Acceptance observes changing rendered output and lifecycle cleanup rather than timer/event counters.
- **Avalonia direction:** Prefer current framework frame scheduling such as `TopLevel.RequestAnimationFrame` for purely visual continuous transforms when implementation research confirms it fits, rather than assuming a fleet of 16 ms UI timers is necessary. Animated asset decoding remains a measured package/implementation choice that must work on both targets. Current API source: [Window/TopLevel animation-frame API](https://api-docs.avaloniaui.net/docs/T_Avalonia_Controls_Window).
- **Consequences:** Initial load, mode changes, mod changes, pause/resume, attach/detach, and teardown must each select exactly one active animation pipeline. A static fallback is valid only when it is visible and the decode failure is reported; it cannot be presented as animation parity.
- **Acceptance:** The rendered-liveness contract in [`capability-inventory.md`](capability-inventory.md#avatartube) passes on Windows and Linux, including repeated lifecycle and all built-in mod transitions.

### A-007: Pi task orchestration supplements the port workflow

- **Problem and current need:** The port spans many behavior contracts, platform spikes, implementation slices, verification gates, and commits. Existing Pi workflows provide domain discipline, while `pi-task` adds deterministic spec phases, persisted crash recovery, sequential `/task-auto` orchestration, and executable verify/enforcement gates.
- **Selected direction:** Admit project-pinned `@mjasnikovs/pi-task 0.18.24` as a development-only orchestration aid. `/task` is used for narrow task-board rows; `/task-auto` is used only for an owner-reviewed milestone document after one pilot task proves clean scope, verification, and commit behavior. The complete operating contract is [`port-workflow.md`](port-workflow.md).
- **Authority boundary:** Generated task files and specs are subordinate to owner decisions, client architecture/capability docs, the live client task board, repository instructions, and required skills. The extension never decides product parity or marks headed behavior verified on its own.
- **Security and licensing:** Pi packages execute with the user's full permissions and can change prompts, tools, files, commands, and git history. The package is AGPL-3.0-only, remains outside product/runtime dependencies, and is not distributed in CCP binaries. Its unauthenticated bidirectional remote server is disabled by default for this project workflow.
- **State and reproducibility:** `.pi/settings.json` records the exact package version. `.pi/npm/` is generated installation state. `.pi-tasks/` is ignored local crash-recovery state; `client/docs/task-board.md` remains the authoritative queue and evidence ledger.
- **Commit safety:** Auto-commit is disabled for the pilot and any dirty/shared worktree. It may be enabled later only in a clean dedicated branch/worktree after proving one-task/one-commit boundaries. A verify override is not completion evidence and cannot authorize automatic fix-in-place enforcement.
- **Acceptance:** Pi meets the package peer requirement, the pinned extension installs with no package-audit findings, `/task` produces a correctly scoped spec, its `VERIFY` block actually runs, the resulting diff stays within scope, task-board evidence is reconciled, and no unrelated files enter the task commit. Only then may the first milestone use `/task-auto`.

### A-008: Multi-model consultation is an evidence-aware review gate

- **Problem and current need:** Port decisions repeatedly cross architecture, parity, platform, rendering, security, performance, and verification boundaries. One executor model can miss assumptions or overcommit to its first approach. The port benefits from deliberate second opinions and dissent, especially inside long `/task-auto` runs.
- **Selected direction:** Admit project-pinned `@booplex/bpx-consult 0.10.1`. Use solo and gut-check for routine bounded review, council for high-impact decisions and gates, and debate for unresolved competing approaches. The extension is available in the main Pi session and whitelisted into `pi-task` child sessions. Detailed checkpoints and question format live in [`port-workflow.md`](port-workflow.md#consultation-gates).
- **Council design:** The project roster covers architect, critic, simplifier, tester, security, and performance perspectives across verified GPT 5.6 Sol/Luna, Fable 5, and Kimi K3 routes; Kimi K3 synthesizes the result. Automatic stuck review triggers after three consecutive tool failures or repeated identical calls. Automatic on-done review remains off; completion consultation is explicit and task-shaped.
- **Authority boundary:** Consultation is advisory. Owner decisions, documented contracts, source code, current official documentation, tests, measurements, and headed evidence outrank advisor confidence or consensus. Splits and failed members are surfaced, not averaged into permission to proceed.
- **Privacy and cost:** Consult forwards a fitted session transcript to external advisor providers. Never expose secrets, signed URLs, private content, camera data, or sensitive logs. Questions must be focused, model-initiated calls are capped, and repeated consultation requires new evidence or a narrower decision.
- **Context integrity:** Every result's kept/compressed/clipped/dropped ledger is reviewed when the decision depends on long-session history. Material clipping requires a fresh focused consult. A confidence score is not valid when decisive context was absent.
- **Acceptance:** Exact package/version and Node/Pi requirements are verified; every configured seat is probe-tested; a pilot `/task` demonstrates pre-approach and pre-completion consultation; advice and dissent are reconciled against empirical evidence; sensitive data is absent; and the client task board records the resulting decision rather than the full transcript.

### A-009: Explicit audio channels and truthful playback lifecycle

- **Problem:** The first attempt used a generic shared player that stopped unrelated playback, returned completion immediately, dropped queued bark audio, approximated busy state with bubble timers, and allowed unreliable detached SFX players. The owner reports sounds and quips were done badly.
- **Selected direction:** Separate policy from playback and use explicit channel ownership: exclusive companion voice, bounded-polyphony SFX, whisper/session voice, video/media, and reference-counted system ducking. Speech items keep text, voice asset, mood, priority, freshness, and cancellation together.
- **Lifecycle contract:** Playback reports accepted, started, completed, interrupted, cancelled, unavailable device, missing asset, and decode failure. Required acknowledgements cannot be silently dropped. Actual backend events own busy state, with bounded watchdogs only for recovery.
- **Platform impact:** Audio is not an Avalonia UI responsibility. Admit a maintained backend only after Windows/Linux spikes prove codec support, low-latency SFX, device enumeration/selection, completion, pause/resume, teardown, packaging, and license. LibVLCSharp `3.10.0` is a current candidate, not yet admitted. Linux ducking remains a capability decision until PipeWire/PulseAudio behavior is proven.
- **Acceptance:** The quip/sound contract in `capability-inventory.md` passes under simultaneous voice, SFX, whisper, and video; output-device failure and all teardown paths are exercised.

### A-010: Provider-neutral, typed, cancellable AI trust boundary

- **Problem:** The first attempt blurred genuine AI, canned fallback, refusal, provider failure, cancellation, and command outcomes; requests lacked end-to-end cancellation; lenient JSON repair could become effect authority; endpoint and awareness privacy boundaries were weak.
- **Selected direction:** Every provider implements one typed operation result and one cancellable request lifecycle. Interactive chat and background awareness are separate operations over shared transport/moderation policy. Provider configuration is captured at request start, and late results are discarded when their generation is no longer current.
- **Command boundary:** AI effects remain opt-in and default off. Only a strict versioned structured envelope may request commands. Moderate and validate the entire payload, enforce per-effect permissions/caps/path allowlists/safety ceilings, and return per-command outcomes. Malformed/mixed output is text-only or a structured failure, never repaired into executable authority.
- **Network/privacy boundary:** Disclose actual endpoint and transmitted data. Treat non-loopback Ollama as remote; invalid endpoint sends nothing; remote HTTP is rejected unless an explicit product decision permits it. Camera/biometric data never enters AI. Secrets use approved OS-backed storage and diagnostics are content-free.
- **Acceptance:** Provider outcome, cancellation, switching, moderation, strict commands, memory, endpoint, offline, secret, and awareness tests in `capability-inventory.md` pass on Windows/Linux.

### A-011: Local deep-learning camera pipeline with one admitted gaze feature

- **Problem:** WPF's local BlazeFace/FaceMesh/Iris pipeline is useful and privacy-preserving. The first attempt extended it with full-face deep gaze but shipped only a Windows implementation, silently fell back between incompatible calibrated features, and referenced model weights whose training-data rights may not permit commercial distribution.
- **Selected direction:** Preserve local deep face/landmark/iris inference as the baseline direction. Separate acquisition, preprocessing/inference, semantic events, calibration, and consumers conceptually without copying old classes. Admit exactly one default gaze feature/model pair only after Windows/Linux accuracy, performance, packaging, and legal provenance pass.
- **Deep gaze:** Full-face appearance gaze is a research spike until weights and training data are commercially distributable and it measurably beats the iris baseline under identical calibration/hardware tests. Do not expose a model selector merely because the first attempt had one.
- **Privacy:** Memory-only frames and biometric derivatives are non-negotiable. Persist only explicit consent metadata, settings, and compact numeric calibration tied to camera, monitor, model hash/version, feature, and preprocessing. Any expansion bumps consent and requires owner review.
- **Platform impact:** Windows and Linux need real capture backends and honest permission/failure states. Sandboxed Linux must prove XDG portal/PipeWire if supported. ONNX Runtime and OpenCvSharp are candidates requiring exact version/license/native-size/runtime spikes; no package is admitted by documentation alone.
- **Acceptance:** Consent, capture, model provenance, calibration, semantic events, privacy audit, performance, failure, and teardown criteria in `capability-inventory.md` pass on both target platforms.

### A-012: Official WPF migration guidance is the translation baseline, not the product architecture

- **Problem:** Earlier work relied on scattered old-port lessons and stale pre-v12 knowledge. Avalonia now publishes a current 2026 WPF migration guide and detailed cheat sheet covering the exact conceptual differences. An older expert methodology article also provides useful project-level preparation advice.
- **Selected direction:** After extracting the user-observable WPF contract, implementation uses the current official [Migrating from WPF](https://docs.avaloniaui.net/docs/migration/wpf/) guide and [WPF to Avalonia cheat sheet](https://docs.avaloniaui.net/docs/migration/wpf/cheat-sheet) as the primary concept-translation baseline, followed by each linked deeper v12 topic page and runtime evidence.
- **Accepted technical guidance:** CSS-like selectors/classes/pseudo-classes instead of WPF triggers; `DataTemplates` collections and `TreeDataTemplate`; strongly typed `StyledProperty`/`DirectProperty` choices; pointer events and routing strategies; direct `ICommand` rather than `RoutedCommand`; asynchronous dispatcher use; Avalonia animation/frame APIs; explicit asset URI conversion; separate-package/missing controls; and `TopLevel.Screens` platform services.
- **Accepted methodology from the older [expert guide](https://avaloniaui.net/blog/the-expert-guide-to-porting-wpf-applications-to-avalonia):** audit dependencies and platform-specific code before implementation, inventory complex views/capabilities, reach a visible vertical slice early, work incrementally, keep small commits, and test functionality/performance on every target platform.
- **Rejected methodology:** The greenfield client does not preserve the old code structure merely because the article says "port, not refactor"; it does not comment out/uncomment the WPF project into a new build, use per-line/per-view estimates as plans, adopt XPF/Hybrid, or add community controls without admission. Owner decisions A-001 through A-011 and behavior-first contracts remain higher authority.
- **Consequence:** Skills and `/task` specs must separate archaeology from translation. The cheat sheet suggests a candidate Avalonia equivalent but never proves behavior, Linux support, performance, focus/input, window semantics, or visual correctness. Targeted tests and headed evidence remain mandatory.
- **Sources:** Official migration index last updated April 2026; cheat sheet last updated June 2026; expert guide published August 2024.

### A-013: AvaloniaUI.MCP is an optional advisory lint and UX ideation source

- **Problem:** Pi can now call [`decriptor/AvaloniaUI.MCP`](https://github.com/decriptor/AvaloniaUI.MCP), which advertises XAML validation, diagnostics, performance, accessibility, theming, controls, animations, testing, and WPF migration assistance. It could accelerate dashboard and UX review, but its output looks authoritative even when stale or generic.
- **Verified upstream state:** The repository has one public commit dated June 2025, no GitHub release, targets .NET 9, uses preview MCP `0.3.0`, and pins Avalonia `11.3.1`. XAML validation is XML parsing plus hand-written heuristics, not compilation with the client's Avalonia v12 toolchain. Generators include stale WPF constructs and questionable Avalonia APIs. Startup config contains a fixed external Sentry DSN with tracing/profiling.
- **Selected use:** After contract extraction and current official v12 research, agents may use the MCP for a bounded second opinion on small redacted AXAML fragments, selectors, bindings, layout, accessibility, diagnostics, and heuristic performance. Its control catalogue and UX tools may suggest candidate primitives or questions for dashboard/cards/popups, but do not establish product design or API validity.
- **Forbidden use:** Do not directly adopt its generated project/architecture, WPF conversion, themes/palettes, custom controls, storyboards/animations, services, data/authentication, tests, package choices, performance scores, or migration claims. It cannot replace CCP's visual grammar, K3 rendered-image review, the real compiler, tests, profiling, or headed Windows/Linux acceptance.
- **Privacy and admission:** Do not send proprietary code, secrets, local paths, user content, camera data, private endpoints, or sensitive logs until the installed server is inspected and outbound telemetry is disabled. MCP unavailability never blocks a task. Accepted/rejected findings are summarized in task evidence.
- **Decision chain for UI:** behavior/visual contract -> current official v12 sources -> smallest hand-authored implementation -> optional redacted MCP review -> compile/tests/headed interaction -> K3 screenshot review.

### A-014: Foundation behavior must be explicit and end-to-end

- **Problem:** First-attempt history repeatedly repaired startup ordering, secret wiring, settings migrations, exit flush, corrupt-file handling, write-order races, cross-thread UI updates, lifecycle leaks, native Release crashes, missing packaged assets, orphaned UI/reactions, misleading capabilities, and code described as verified while still unwired.
- **Selected direction:** The greenfield foundation defines six explicit contracts before broad feature work: startup/shutdown phases, typed runtime capabilities, persistence/schema migration, async/lifecycle ownership, asset/mod/localization packaging, and Debug/Release/publish verification. The evidence and dispositions are in [`first-attempt-systemic-lessons.md`](first-attempt-systemic-lessons.md).
- **Capability rule:** Registration, OS identity, copied assets, and a non-throwing fallback do not establish support. Capabilities report available, unavailable with reason, degraded with named semantics, permission/dependency required, or faulted, and promised behavior requires a runtime probe.
- **Integration rule:** Unit-tested or registered but unwired code is infrastructure only. A product capability closes only after one real composition-root-to-user-outcome path passes.
- **Lifecycle rule:** Long operations have an owner, cancellation generation, completion task, typed terminal outcome, and idempotent teardown. Required work cannot disappear into detached tasks or blanket catches.
- **Persistence rule:** User data has one schema/migration/atomic-write/recovery authority. Unreadable data is preserved, secrets are excluded, concurrent writes are serialized, and graceful shutdown flush is explicit.
- **Release rule:** Debug, Release, and published artifacts are separate gates. One version source drives assemblies, update metadata, and packaging.
- **YAGNI constraint:** Establish these contracts through the first concrete vertical slices. Do not create a generic framework or platform seam without a real consumer/boundary.
