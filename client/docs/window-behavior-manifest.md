## 3. Observation procedure per field (how the exercise gate will exercise every row)

General harness rules: Windows procedures use the SP-007/SP-008 headed harness patterns (real `SendInput` input, UIA reads, pixel captures; window raised via `SetWindowPos(HWND_TOPMOST)` on `Process.MainWindowHandle` when occluded — SP-007 surprise #2). Linux procedures use `wmctrl -l`/`-lx`, `xprop -id`, `xwininfo`, and XGetImage captures (python3 ctypes + libX11 — SP-007 surprise #3); **WSLg has no xdotool and no passwordless sudo (SP-007 named gate) — input-injection steps are "procedure defined, not demonstrable on WSLg" and are executed Windows-headed; property-level steps (xprop/wmctrl/XGetImage) are demonstrable on WSLg as session facts.** Each row in §4 names the variant that applies where it deviates from the generic procedure.

| Field | Windows procedure | Linux (WSLg/X11) procedure |
|---|---|---|
| **Category** | Not directly observable; asserted by the row's other fields passing their category variants (e.g. a "non-activating notification" must pass the focus-did-NOT-move activation variant) | Same |
| **Owner** | Win32 `GetWindow(hwnd, GW_OWNER)` on the live window (harness P/Invoke); behavioral: activating the owner raises the owned window with it; closing the owner cascades-close the child | `xprop -id <wid> WM_TRANSIENT_FOR` present and equals the owner's window id; `xprop _NET_WM_WINDOW_TYPE` = `_NET_WM_WINDOW_TYPE_DIALOG` for dialogs; cascade-close observed via `wmctrl -l` before/after closing the owner |
| **Modality** | Modal: while open, click the owner (SendInput) — owner does not activate, UIA focus stays in the dialog. Modeless: click the owner — owner activates and remains usable while the child stays open | Input-injection variant not demonstrable on WSLg (no xdotool); property evidence: `_NET_WM_STATE_MODAL` on the modal window via `xprop` |
| **Activation / initial focus** | Activating (default): after open, `GetForegroundWindow` = the new window; UIA `FocusedElement` recorded. **Non-activating variant (notifications):** foreground window AND focused element UNCHANGED after the surface appears (assert focus did NOT move). **Focus-restoration variant:** after close, foreground/focus returns to the owner | `xprop -root _NET_ACTIVE_WINDOW` before/after open and close (session facts) |
| **Taskbar / Alt-Tab** | Taskbar: window title present/absent in the shell taskbar (UIA on `Shell_TrayWnd` or headed screenshot). Alt-Tab: harness sends Alt+Tab, captures the switcher (screenshot), asserts presence/absence per row | `wmctrl -l` (`_NET_CLIENT_LIST`) for taskbar presence; Alt-Tab switcher is compositor-owned on WSLg — procedure defined, demonstrable only as `_NET_CLIENT_LIST` + `_NET_WM_WINDOW_TYPE` session facts |
| **Topmost** | Win32 `GetWindowLong(GWL_EXSTYLE) & WS_EX_TOPMOST` on the live handle; **dynamic rows** sampled before AND after the coded transition trigger (e.g. SessionComplete `ContentRendered`) | `xprop _NET_WM_STATE` contains `_NET_WM_STATE_ABOVE`; dynamic rows sampled at the same triggers |

| **Decorations** | Pixel capture: `WindowStyle.None` rows show no native title bar/border (custom chrome); drag the row's coded drag surface (custom title bar) — window moves; grip visible for `CanResizeWithGrip` | XGetImage capture for native-chrome absence; drag is input-injection (not demonstrable on WSLg) |
| **Close / reuse lifecycle** | Close via the row's affordance (close button / coded Escape); assert instance gone from UIA enumeration. Reopen: dialogs → NEW instance with fresh state; singleton rows → the coded reuse (e.g. `ChaosHubWindow.Current` activate, `HelpVideoWindow` close-then-new, `FeaturePopupWindow` one-at-a-time, `LockCardWindow` pool rent). Owner-close cascade. App-shutdown path: closing the root exits 0 (SP-003 teardown) | Same via `wmctrl -l` enumeration + process exit code; instance-identity nuance (pool reuse) is Windows-headed evidence |

## 6. Shared-chrome implications (constraints only — no chrome design)

What this manifest CONSTRAINS for any future shared-chrome decision:

1. **No blanket policy.** Behavior is per-row: the same codebase mixes modal/modeless on ONE window (W-16), topmost-pulse-then-drop lifecycles (W-43, W-66, W-77), and per-call-site parameters (W-12). Shared chrome must be parameterized per window contract, not applied as one dialog/window style (also the first-attempt lesson: "Similar-looking windows share one behavior" — REJECTED).
2. **Custom chrome is the dominant shape.** MainWindow + most dialogs + all attention/notification surfaces are `WindowStyle.None` (many with `AllowsTransparency=true`). Shared chrome must supply usable move/close/(min/max per the row's resize field) for `None`-style windows; editors with native chrome (W-05, W-06, W-08, W-18, W-22…W-24, W-48…) must not be forced into it.
3. **Transparency is load-bearing.** `AllowsTransparency=true` underlies rounded custom chrome on the majority of custom-chrome rows. A shared-chrome decision needs a per-platform transparency capability story (probe-derived per the capability contract) before it can promise these rows on Linux.
4. **CenterOwner must mean the owner's monitor.** The dominant dialog placement is `CenterOwner` (40+ rows); owner-monitor working-area math (not primary-monitor) is a hard constraint, shared with the popup-scrolling row's owner-monitor rule.
5. **Owned-non-taskbar surfaces lose focus to the background on close.** W-04's explicit unminimize+`Activate()` restoration exists because `ShowInTaskbar=false` owned windows let WPF activate whatever is behind. Shared chrome/lifecycle must own explicit focus restoration for this shape.
6. **Non-activation is a first-class surface type.** Notifications (W-71…W-75) and overlays require show-without-focus; chrome must support non-activating presentation, and the exercise gate asserts focus-did-not-move.
7. **Dynamic topmost transitions are required.** Several rows change `Topmost` after show (W-43, W-66, W-76) or per call site (W-12) or conditionally (W-03). Chrome must permit runtime topmost transitions, not a static flag.
8. **Lifecycle ownership differs per row.** Singleton reuse (W-02, W-12), one-at-a-time (W-04), close-existing-before-new (W-11), keep-alive pools (W-62), single-field (W-70, W-77), modal re-open loops (W-67). A shared window-registry/lifecycle must express these, not assume new-instance-per-open.
9. **Modality is not a type property.** W-16 is modal at three call sites and modeless at a fourth. Chrome cannot hard-code modality per window class.
10. **Escape/close semantics are per-row.** Commit-on-Enter vs cancel-on-Escape (W-70), Esc/F11 fullscreen exit (W-14, W-15), lockdown-blocked close (W-01), minimize-to-tray instead of exit (W-01). Key handling and close veto live in the row contract, not in shared chrome.
