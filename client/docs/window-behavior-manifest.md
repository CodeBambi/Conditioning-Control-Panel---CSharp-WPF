## 3. Observation procedure per field (how the exercise gate will exercise every row)

General harness rules: Windows procedures use the headed harness patterns (real `SendInput` input, UIA reads, pixel captures; window raised via `SetWindowPos(HWND_TOPMOST)` on `Process.MainWindowHandle` when occluded — harness surprise #2). Linux procedures use `wmctrl -l`/`-lx`, `xprop -id`, `xwininfo`, and XGetImage captures (python3 ctypes + libX11 — harness surprise #3); ~~WSLg has no xdotool and no passwordless sudo (a named gate) — input-injection steps are "procedure defined, not demonstrable on WSLg".~~ **CORRECTED 2026-08-24 BY MEASUREMENT: input injection IS demonstrable on WSLg, and the 'no xdotool' gate was a wrong inference from a true fact.** `xdotool`, `xwd`, `wmctrl` and `scrot` really are all absent from the image - but the X server advertises **XTEST 2.2** and `libXtst.so.6` ships in the base X client libraries, so synthetic input needs NO new package, exactly as `XGetImage` needed none. A MISSING TOOL IS NOT A MISSING CAPABILITY. Driven through ctypes by `client/tools/verify/xinput.py`: one XTEST left-click on the Companion door moves it from `rail-door-unselected-border` to `rail-door-selected-border` while the Studio door goes the other way - the same door either side of one gesture. Focus is asserted too: `XGetInputFocus` and the window manager's `_NET_ACTIVE_WINDOW` both name the app window. Each row in §4 names the variant that applies where it deviates from the generic procedure.

## 6. Shared-chrome implications (constraints only — no chrome design)

What this manifest CONSTRAINS for any future shared-chrome decision:

1. **No blanket policy.** Behavior is per-row: the same codebase mixes modal/modeless on ONE window (W-16), topmost-pulse-then-drop lifecycles (W-43, W-66, W-77), and per-call-site parameters (W-12). Shared chrome must be parameterized per window contract, not applied as one dialog/window style (also the first-attempt lesson: "Similar-looking windows share one behavior" — REJECTED).
2. **Custom chrome is the dominant shape.** MainWindow + most dialogs + all attention/notification surfaces are `WindowStyle.None` (many with `AllowsTransparency=true`). Shared chrome must supply usable move/close/(min/max per the row's resize field) for `None`-style windows; editors with native chrome (W-05, W-06, W-08, W-18, W-22…W-24, W-48…) must not be forced into it.
3. **Transparency is load-bearing.** `AllowsTransparency=true` underlies rounded custom chrome on the majority of custom-chrome rows. A shared-chrome decision needs a per-platform transparency capability story (probe-derived per the capability contract) before it can promise these rows on Linux.
4. **CenterOwner must mean the owner's monitor.** The dominant dialog placement is `CenterOwner` (40+ rows); owner-monitor working-area math (not primary-monitor) is a hard constraint, shared with the popup-scrolling row's owner-monitor rule.
5. **Owned-non-taskbar surfaces lose focus to the background on close.** W-04's explicit unminimize+`Activate()` restoration exists because `ShowInTaskbar=false` owned windows let WPF activate whatever is behind. Shared chrome/lifecycle must own explicit focus restoration for this shape.
6. **Non-activation is a first-class surface type.** Notifications (W-71…W-75) and overlays require show-without-focus; chrome must support non-activating presentation, and the exercise gate asserts focus-did-not-move.
7. **Dynamic topmost transitions are required.** Several rows change `Topmost` after show (W-43, W-66, W-76) or per call site (W-12) or conditionally (W-03). Chrome must permit runtime topmost transitions, not a static flag.
8. **Lifecycle ownership differs per row.** Singleton reuse (W-02, W-12), one-at-a-time (W-04), close-existing-before-new (W-11), keep-alive pools (W-62), single-field (W-70, W-77), modal re-open loops (W-67). A shared window-registry/lifecycle must express these, not assume new-instance-per-open.

10. **Escape/close semantics are per-row.** Commit-on-Enter vs cancel-on-Escape (W-70), Esc/F11 fullscreen exit (W-14, W-15), lockdown-blocked close (W-01), minimize-to-tray instead of exit (W-01). Key handling and close veto live in the row contract, not in shared chrome.

## 8. Greenfield native-window layer — input passthrough and capture (added 2026-08-24)

**What this section is, and what §1–§7 are not.** §1–§7 inventory the WPF product's windows. This section inventories the **greenfield client's own native windows** — every site under `client/src/CcpClient.Desktop` that creates a Win32 top-level window, plus the one site that MUTATES an Avalonia window's extended style. It exists because nothing named them together: each site declared (or failed to declare) its own policy at its own creation call, so a seventh surface could invent an eighth policy and no document or test would notice.

It adds **exactly two fields** to the §1.2 vocabulary — **input passthrough** and **capture** — and one **provenance** tag. It changes no behaviour, no flag, and no API; product code was not edited to land it.

**Capture is RECORDED here, never decided.** `client/port.txt:34-35` reserves BROADENING the capture boundary to the owner; it does not reserve writing down what is already true. Nothing in this section calls `SetWindowDisplayAffinity`, adds capture exclusion, or changes any surface's capture behaviour. The `overlay-clickthrough` skill is explicit that capture visibility is per feature contract and must NOT be inferred from click-through or shared composition, so **no capture value below is derived from an input value**; where the code declares nothing, the answer is `UNEXAMINED`. Architecture A-001 notes `SetWindowDisplayAffinity` applies at WINDOW scope, which makes capture policy an INPUT TO the compositor's window-count decision rather than a peer of it — recording it now is what makes that decision possible later.

### 8.1 The two new fields (vocabulary)

- **Input passthrough** — where the window manager routes a click at the surface's own rectangle: **pass-through** (past it, to whatever is underneath) or **absorbing** (to it). The field records the OUTCOME, never the flag that was asked for; `Overlay/Win32OverlayPresence.cs:504-511` measured a run in which every style write SUCCEEDED and the extended style read back wrong anyway. Parameterised sites record the governing expression (§1.3), never a flattened boolean.
- **Capture** — whether the surface is visible to a screen capture or recorder **as a declared policy**. On Windows that policy is expressed by `SetWindowDisplayAffinity` at window scope. `UNEXAMINED` means no site declares one. `d(WDA_NONE)` is the §1.3 default marker: the Win32 default that FOLLOWS from never making the call, recorded as the consequence of an omission and never as a decision somebody made.

### 8.2 Provenance — exactly three legal values

| Tag | Means |
|---|---|
| `runtime-enforced` | The site reads the operating system or the window manager back and **refuses in type** when the answer is wrong. Strictly stronger than any document, because it holds at run time on the user's machine and not merely in review. |
| `upstream-cited` | The site DECLARES its policy at the creation call with a WPF `File.cs:line` citation, and nothing reads the result back. |
| `UNEXAMINED` | Neither. **An honest value, not a gap to be filled by opinion.** It means the code never declared a policy at this site — which is a different statement from "the policy is X and nobody wrote it down". |

Three rules bind this column. (1) The tag is **per site** and records the **strongest thing THE CODE does** about that site's INPUT policy — several sites are both cited and enforced, and those read `runtime-enforced`. (2) **Capture provenance is uniformly `UNEXAMINED` across all seven sites**, so it carries no per-site variation and no separate column; see §8.1. (3) A tag is never upgraded by a reader who examined a site and formed an opinion about what it must have meant.

### 8.4 The census guard (one, tree-wide)

`client/tests/CcpClient.Tests/NativeWindowCensusTests.cs`.

**One guard, not seven.** There are deliberately NO per-surface style guards. S-01 through S-05 already read the OS or the window manager back and refuse in type, which is stronger than any assertion a test could restate; a lexical duplicate would create a second authority that can drift from the first. And a per-surface guard over the `UNEXAMINED` rows would freeze exactly the undeclared accident this section exists to expose.

What the guard does instead: it **re-derives the site set from the shipping bytes** of `client/src` on every run — every occurrence of `CreateWindowExW` and of `AddWindowStylesCallback` is classified as a call site, a P/Invoke declaration, or prose, and an occurrence it cannot classify is a hard failure — and requires that derived set to equal the `File.cs:line` rows of §8.3 exactly, in both directions. It also closes the §8.2 vocabulary and requires any capture value that is NOT `UNEXAMINED` to cite the `File.cs:line` where the policy is made.

Consequences, which are the point: a **ninth native window** with no §8.3 row reds it; a row whose cited line no longer holds its creation call reds it (set equality is over `file:line`, so a citation cannot rot silently); a fourth provenance value reds it; and a capture claim asserted without a citation reds it. What it does NOT do is pin which flags a site may use — freezing those would make this document an authority over behaviour rather than a record of it.

It was still an unknown base — if any Avalonia path (a transparency hint, a future backend change) ever contributed `WS_EX_TRANSPARENT`, the OR would silently keep it, the tunnel would stop receiving the power-up raycast clicks its whole interaction depends on, and **nothing would notice**: S-07 is the one interactive site with no read-back. Recorded as a defect with its evidence, per this section's no-behaviour-change rule.

**RESOLVED 2026-08-25, and one sentence above was wrong.** The fix is the one-line `& ~WS_EX_TRANSPARENT`, now living in `ChaosTunnelWin32.TunnelExStyle` (`Features/Chaos/ChaosTunnelWin32.cs:62-63`) and pinned over every base the seam can hand in, including one that already carries the flag (`CcpClient.Tests/ChaosTunnelExStyleTests.cs:37-73`; reverting the clear to the plain OR reds it at `Expected: 0 / Actual: 32`). **NO LIVE DEFECT EXISTED**, and that was established from the package rather than assumed: decompiled against the pinned Avalonia 12.1.1, `WindowImpl.UpdateWindowProperties` builds the ex-style it hands to the callback from a literal every time — `WS_EX_WINDOWEDGE`, plus `WS_EX_NOREDIRECTIONBITMAP` when the redirection bitmap is off and `WS_EX_APPWINDOW` when `ShowInTaskbar` — never reading the HWND back and never contributing `WS_EX_TRANSPARENT`. **The wrong sentence is "the Avalonia seam runs once at native-window creation":** it does not. The combined callback is invoked from `UpdateWindowProperties`, i.e. on every window-property update — four times in one second on the headed run below. That is nearer to upstream's per-re-show hazard than this record claimed, and it is why the cheap insurance was taken rather than closed as unreachable. **What the clear does NOT cover, stated because the obvious guess is wrong:** `AddWindowStylesCallback` is a `Delegate.Combine`, and a multicast delegate with a return value hands every callback the SAME original base and applies only the LAST one's return. So a second styles callback on this window would discard S-07's flags outright rather than poison its base — last-writer-wins, not a chain — and no clear defends against that. Measured, not reasoned: a probe callback registered second returned the base unchanged and the window read back `0x00200000`, the product's two flags gone.

**Headed evidence, Windows only, 2026-08-25.** A probe opened the real shipped `ChaosTunnelWindow` on a real desktop. The base Avalonia contributed was `0x00200100` (`0x00240100` with `ShowInTaskbar`) — `WS_EX_NOREDIRECTIONBITMAP + WS_EX_WINDOWEDGE`, no `WS_EX_TRANSPARENT`, matching the decompiled literal exactly. The shipped window's live `GWL_EXSTYLE` read back **`0x08200080`** — `WS_EX_NOACTIVATE + WS_EX_NOREDIRECTIONBITMAP + WS_EX_TOOLWINDOW`, `WS_EX_TRANSPARENT` CLEAR — and unchanged after two window-property updates. **That establishes the window is hit-testable at the Win32 level; it is NOT the click claim.** No run has navigated the tunnel page in a WebView2, synthesised a press over it and had the page report the hit, so "clicks reach the page" stays unproven. Nothing here is a Linux claim: the callback is skipped entirely off Windows.

### 8.7 The topmost claim: bare, not through the attach ladder — DECIDED 2026-08-25, and decided on a measurement

**The question.** `Win32OverlayPresence`, `Win32GlyphSurface`, `Win32VideoPresence` and `Win32PointerSurface` all assert `HWND_TOPMOST` with a plain `SetWindowPos` and nothing in front of it. The repo owns a foreground-escalation ladder — `Win32InputPresence.Escalate` (`Input/Win32InputPresence.cs:692-715`) — and a process that has lost `SetForegroundWindow` permission has its topmost claim refused **with a success return**. Should the four route their claim through the ladder?

**The decision is NO, and the four keep the bare claim.** Guard: `client/tests/CcpClient.Tests/TopmostAssertionPolicyTests.cs`.

**What the ladder actually buys and what it costs — measured, not reasoned.** A standalone Win32 probe, no product and no test code in it, three runs on this machine: a `WS_EX_TOOLWINDOW + WS_EX_NOACTIVATE` popup, `SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE)` bare, then the same call preceded by `Escalate`'s exact sequence (`AttachThreadInput` to the foreground thread, then `SetForegroundWindow` + `BringWindowToTop` + `SetActiveWindow` + `SetFocus` on the target, detached in a `finally`).

| Leg | `SetWindowPos` return | last-error | `GWL_EXSTYLE` read back | `WS_EX_TOPMOST` | Surface is foreground |
|---|---|---|---|---|---|
| bare, process without the permission | `TRUE` | 0 | `0x8000080` | **absent** | no |
| bare, process with the permission | `TRUE` | 0 | `0x8000088` | present | no |
| `Escalate` then the same bare call | `TRUE` | 0 | `0x8000088` | present | **YES** |
| bare on a NEW window after `Escalate` | `TRUE` | 0 | `0x8000088` | present | no |

Three facts come out of that table and each one is load-bearing.

1. **The ladder works, and its mechanism is the thing these four surfaces exist to avoid.** It restored the band — and it made a `WS_EX_NOACTIVATE + WS_EX_TOOLWINDOW` popup the FOREGROUND WINDOW, taking the foreground off a window belonging to another process (`foregroundBefore=0x23B0444`, `foregroundAfter` = the probe's own popup, in both runs where it was recorded). `WS_EX_NOACTIVATE` stops a CLICK from activating a window; it does not stop an explicit `SetForegroundWindow`. All four surfaces are non-activating by contract, and `Win32OverlayPresence` **refuses in type on exactly this outcome** — `overlay-stole-focus`, "the surface interrupted whatever the user was doing" (`Overlay/Win32OverlayPresence.cs:583-585`). So routing the topmost claim through the ladder would trade a `style-refused` for a `stole-focus` refusal in the same run, and pay for it with a real focus theft — inside a loop bounded at 32 iterations per hit-test question (`Overlay/Win32OverlayPresence.cs:652`).

2. **The write's return value is worthless and the read-back is the whole product.** `SetWindowPos` returned `TRUE` with last-error 0 in **every leg of every run**, including the leg where the bit was not applied. That is the same shape §8.1 already records from the other direction — a run in which every style write SUCCEEDED and the extended style read back wrong anyway (`Overlay/Win32OverlayPresence.cs:504-511`). The four surfaces already refuse on the OS's own read-back and walk the real z-order rather than trusting the flag, which §8.2 ranks strictly stronger than any declaration. Asserting harder does not make a refused claim true; it makes a refused claim louder.

3. **The permission is not the process's to hold, and this bench proved it the uncomfortable way.** Two runs of the identical script, minutes apart on a quiet machine, disagreed about whether a fresh process could place a window in the topmost band at all — the first run's very first leg read back `0x8000080` with no `0x8`, and later runs read `0x8000088`. **The board's exact poisoning recipe was NOT reproduced here** (the probe's synthetic click did not land on its own window — `WindowFromPoint` answered a different HWND — so that leg is unproven in this measurement), and the negative case appeared once and could not then be forced back. What IS established is the direction that matters: the outcome of a topmost claim is adjudicated by the OS against process state this code does not control, so the only honest posture is to read the result back and refuse. That is what ships.

**The two deferral reasons from 2026-08-23 still hold and are not weakened by having measured the ladder.** The state is not user-reachable — the shipping app always owns a top-level window (the Avalonia main window, or `Tray/Win32TrayPresence.cs:452`'s hidden owner) — and the one route that reached it inside the suite was closed at its cause by the per-test-thread window floor rather than by repairing permission afterwards. And `AttachThreadInput` against a FOREIGN foreground thread couples this process's UI thread to another process's for the duration, whose failure mode is not a refused grab but a frozen app; `Input/Win32InputPresence.cs:660-669` states that risk at the one place somebody would change it, and nothing in the suite exercises it against a hung foreign thread.

**What would re-open this.** A measured case where a user-reachable path leaves a surface refused for the rest of the process's life. Not a `style-refused` line in a log: that line is the surface working. The remedy if it ever does re-open is also not this ladder — it is the same shape the suite already took, keeping a window alive so the permission is never revoked, which costs no foreground and no foreign-thread attach.

**No Linux claim.** All five topmost-asserting files are `Win32*` types that do not exist off Windows (§8.5), and the probe above is a Win32 probe.
