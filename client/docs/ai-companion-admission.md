## 2. Provider design

1. **Strategy seam (contract §3 rule 1, ADAPTED):** providers carry stable typed IDs; exactly one is *selected*; selection is a settings-level fact (WPF baseline: `CompanionPrompt.AiProvider`, default Cloud — `CompanionPromptSettings.cs:27`). The WPF/first-attempt live per-call switch with no generation handling (`AiServiceStrategy.cs:22-58`) is **REJECTED**.
2. **Switch = generation invalidation → token cancellation → stale-application discard** (contract §3 rule 2, §2; SP-004 mechanics reused, no new async machinery). A reply started under provider A can never be displayed, executed, or remembered after a switch to B. This is the row's "provider switching without late results" acceptance; proven at pipeline level in c1 and live against a real in-flight network operation in c2 (SP-019 item 1 shape, in-product).
3. **Selection ≠ availability** (contract §3 rule 3, §11 rule 2): a selected-but-unproven provider yields `AiReply.Unavailable(reason)` and an SP-006 typed capability state. c1 proves this typed consequence against the cloud-absent reality (no credentials exist — §2 rule 6); the rejected shapes are WPF's identity-check `IsAvailable` (`AiService.cs:52`) and local always-true (`LocalAiService.cs:46`).
4. **Badge/status honesty (contract §1):** the `AiReply.Generated(text, provenance)` provenance field — and nothing else — drives the AI badge; `Fallback`/`Unavailable`/`Refused` are distinguishable by type and never badged (WPF baseline mechanism: `IsAiGenerated` → badge, `Speech.cs:319-353`; the bool is superseded by the typed variants). Status surfaces read the SP-006 capability state, never a registration/selection fact. The headed accuracy proof lands in c7 (§8 mapping says so explicitly).
5. **Endpoint classification + admission policy (contract §6):** classification is pure host-shape analysis from configuration alone — `Loopback` / `FirstPartyCloud` / `RemoteHostOllama` / `ThirdPartyCloud`; no probes. The admission-policy seam ships with a **loopback-only placeholder policy** (the SP-019 spike shape, item 7: every non-loopback endpoint rejected *before any socket opens*, send-attempt counter proof) until the owner answers the allow-list question (§9). Remote-host-Ollama is remote for disclosure purposes (first-attempt rejected assumption "local AI = local-only data"; WPF accepts any absolute URI, `LocalAiService.cs:244-269` — gap closed).
6. **Cloud (FirstPartyCloud) = inventory, not admission (contract §6 rule 4).** The proxy endpoint and V2/V1 auth shapes are recorded as inventory facts (`AiService.cs:27,332-352,479-499`). **No cloud provider slice is cut**: no credentials exist on the evidence box and none are invented (SP-019 named limit 9); building unverifiable network code would violate the honesty framing. The cloud provider's *typed absence* is live product behavior from c1 (rule 3). A future slice owns cloud implementation when credentials exist — named in §9.
7. **No discovery, no health probes, no fallback chain** (contract §3 rule 4): silent endpoint fallback is rejected; the WPF V2→V1 404 fallback (`AiService.cs:355-361`) is recorded as inventory, and any future disclosed-fallback chain is an owner decision with typed transitions.
8. **Offline = zero network (contract §11):** when no provider is proven available the subsystem performs no outbound AI traffic — no speculative retries, no endpoint guessing. Proof shape (c1/c2): the SP-019 send-attempt-counter discipline — an offline integration test asserts zero outbound attempts, and loopback operations degrade independently of cloud (§11 rule 4).

## 3. Moderation design

1. **Boundary placement (contract §7 rules 1–2):** input side — every text field entering an AI request (chat input, awareness context fields, prompt templates: user-authored preset sections, community prompts, quiz templates); output side — every model-produced text field shown, spoken, persisted, or executed; **every free-text command field** (subliminal text, mantra text, bounce words, media titles) pre-execution. The WPF inventory proves the gap this closes: exactly 4 call sites exist (`AiService.cs:274,409`; `LocalAiService.cs:415,555`; `QuizService.cs:561`) and **command fields are never moderated** (first-attempt command path gates on toggles only, `CCP.Avalonia/Services/Commands/AiCommandService.cs:87-103` — lessons-only evidence). The keyword-trigger pre-check deliberately removed in WPF (`KeywordTriggerService.cs:1294-1301`, H7) is superseded: the boundary is uniform, and per-surface hit accounting is a policy-value matter (§9), not a reason to skip a surface.
2. **Verdict taxonomy (contract §7 rule 3):** `Pass` / `Block(category, surface)` / `SoftHit(category, surface)`; refusals are typed values carrying `ModerationSource` and category. The sentinel-string channel (`ModerationRefusal.cs:53-54`) is **REJECTED**. Awareness-class operations drop refusal/unavailable outcomes silently *by type* (contract §4 rule 3 — no out-of-context refusal bubble; the WPF call-site convention retained as typed behavior).
3. **Guard outside the model (contract §7 rule 4):** user-authored prompt sections can never widen or bypass the guard (AI_AUDIT §7 records WPF's prompt-side-only refusal as the failure this closes).
4. **Escalation mechanism (greenfield-decision, WPF baseline facts):** WPF runs a 3-hit one-shot warning / 5-hit cooldown counter on user chat input only (`ModerationCounter.cs:84-85,108-125`). The *mechanism* (typed hit counter + cooldown state consulted at operation admission) is admitted; the *threshold values* fold into the moderation-policy owner question (§9) with the WPF values recorded as baseline, not decision.
5. **Policy VALUES owner-pending (contract §7 rule 5):** category list, wordlist contents, soft-hit handling. The design functions with typed placeholders: the guard evaluates an injected policy document whose default is the SP-019 "verdict-rejected shape only" posture; no category or wordlist is invented here.
6. **F1 duplicate-key fix:** the SP-019 finding (`System.Text.Json` last-wins vs `EnumerateObject` sees-all — a parser-differential hazard against contract §8 strict-schema intent) is assigned to **c1** (first slice touching the AI code; fix = reject duplicates, the only contract-consistent answer per SP-019; the 62 fuzz cases are the regression proof). It is hardening of the same strict-boundary machinery this section governs, so it is recorded here and mapped in §8.

## 4. Memory design

1. **What is stored:** per-turn user/assistant chat pairs, provider-neutral (contract §5 rule 3). System prompts, enrichment blocks, and awareness/ambient reactions are **never** persisted (WPF precedent: stateless ambient path, `LocalAiService.cs:476-502`; persist skips system/enrichment, `:107-135`). Memory content never flows into diagnostics (contract §12 rule 3) and is never a secret (contract §10).
2. **Where — DECIDED: SP-005 machinery, no new seam.** One `PersistenceStore<AiMemoryDocument>` in the user-data root with its **own** named `AsyncOperationOwner` (the SP-024 lesson: N stores sharing one owner cancel each other's writes), schemaVersion + migration journal, corrupt document quarantines once at startup → typed `Degraded` (the b2/b4 precedent). **Rejected alternative:** a dedicated memory-persistence seam — it duplicates migration/quarantine/schema machinery the persistence contract already owns, for zero gain (pre-approach consult, recorded in record.md §5). `IAiMemoryStore` (SP-016, declared-only) is the *access* interface; SP-005 is the *storage* machinery behind its first implementation.
3. **Retention (owner-pending, placeholder-shaped):** pair-cap value (WPF baseline: 50 pairs, `LocalAiService.cs:92`) and disable semantics (retain dormant vs delete — task-board "Decisions needed") are owner questions (§9). The document schema is shaped so **both** answers are implementable additively without schema change (consult condition): the disable flag and the retention policy are orthogonal fields; a `dormant` marker is representable from v1.
4. **Explicit clear (row acceptance):** an explicit-clear operation exists and is user-reachable — it empties in-memory state and deletes the persisted document (WPF precedent: `ClearHistory()` + file delete, `LocalAiService.cs:173-178`; UI callers `MainWindow.Patreon.cs:962,1539,1570`). The operation lands in c4 (with file-content proof); the user-facing control lands in c7 (§8 mapping). Provider switching never implicitly clears memory (contract §5 rule 3).
5. **Consent gating (contract §5 rule 2):** memory writes occur only under an explicit memory-consent state, code-enforced at write admission. Scope (global vs per-feature) and default are owner-pending (§9); WPF baseline fact: `ChatMemoryEnabled` default **true** (`CompanionPromptSettings.cs:120`). Persist is deferred until output moderation passes; a blocked turn is rolled back and never hits disk (WPF precedent `LocalAiService.cs:546-586` — admitted as design rule).

## 5. Awareness design

1. **Consent, code-enforced (contract §4 rule 1):** awareness operations run only under an explicit typed awareness-consent state checked at operation admission — never a prompt convention. WPF baseline: `AwarenessModeEnabled` AND `AwarenessConsentGiven`, both default false (`WindowAwarenessService.cs:337-338`; `AppSettings.cs:2982,2993`). Consent granularity (per-context-field? per-source?) and defaults are owner-pending (§9); the seam is shaped so granularity answers tighten without contract change.
2. **Context packaging:** the `[Category | App | Title | Duration]` shape (`AiService.cs:160-163,182-188`) is the WPF-observed baseline for what an awareness operation transmits. Every transmitted field passes the moderation input boundary (§3 rule 1), transmission occurs only under consent (rule 1), and context fields **never** enter diagnostics or memory (contract §12; §4 rule 1). Window-title observation itself is platform evidence: c5 records WSLg/X11 session facts for title capture and names any backend gap honestly (no Wayland claim anywhere).
3. **Cooldowns — mechanism designed, values owner-pending (contract §4 rule 2):** typed per-trigger, global, per-keyword, and loop-protection cooldowns with **extend-not-shrink** semantics (WPF mechanisms: `KeywordTriggerService.cs:158-187`; gates `:590-591,604-605`; reaction cooldown `WindowAwarenessService.cs:374-402`). A cooldown-suppressed operation terminates `Completed` with typed `Suppressed(cooldown)` — observable, never a silent no-op. WPF baseline values recorded as facts, **not decisions**: reaction cooldown effective default 10s (`AppSettings.cs:3000-3008`, clamp 10–600) — with the recorded discrepancy that the service's `?? 90` fallback (`WindowAwarenessService.cs:374-388`) is dead code against the non-nullable 10s default (owner question: 10 or 90?); keyword global 10s (`AppSettings.cs:4294`); per-keyword 15s (`:4314`); loop protection 5s (`:4438,4450`); still-on milestones 1/5/10 min (`WindowAwarenessService.cs:405-407`).
4. **Keyword-trigger routing:** the `AvatarComment` routing shape (`KeywordTriggerService.cs:1280-1328`) is admitted with two corrections: the fire-and-forget `Task.Run` becomes an SP-004 owned awareness operation (panic-cancellable, §7), and the "AI unavailable → canned phrase unbadged" fallback becomes typed `AiReply.Fallback`/`Unavailable` visibility per §2 rule 4 (the badge always reflects the true source — the WPF `aiGenerated`-reflects-actual-source behavior retained, the string channel rejected).
5. **Interactive vs awareness distinction (contract §4):** interactive failures surface as typed user-visible state; awareness failures drop by type. Quiz-style stateless multi-turn is an interactive consumer with in-memory history only (WPF baseline `QuizService.cs:175`), never the persistent memory store.

## 6. Secrets and offline

1. **Secret seam = SP-005's `ISecretStore`, reused unchanged** (contract §10 rule 2): settings documents carry opaque secret *names*, never values (WPF precedent: `AppSettings.AuthToken` routes through the Core seam, `CCP.Core/Models/AppSettings.cs:4005-4008`). First implementation lands in c1 as part of the foundation.
2. **Platform backends (greenfield-decision, WPF discipline as baseline):** Windows = DPAPI `ProtectedData` `CurrentUser` scope (WPF precedent `SecureAuthTokenStore.cs:40,66`; `DiscordTokenStorage.cs:52-55`). The implementing slice verifies the Linux backend with evidence and records the admission (contract §10 rule 3 pattern). In-memory secret caches are wiped at teardown (WPF precedent `App.xaml.cs:3299-3300`).
3. **Offline zero-network proof shape (contract §11 rule 3):** the SP-019 send-attempt-counter discipline becomes a product-test shape: with no proven provider, an integration test drives interactive + awareness + command paths and asserts zero outbound socket attempts; endpoint classification remains config-pure (no probe-to-classify, contract §6 rule 2). Loopback and cloud classes degrade independently (§11 rule 4).

## 7. Panic cancellation

1. **Mechanism = the same machinery as provider switching (contract §2 rule 3):** panic/owner-stop increments the generation, cancels in-flight AI work with typed `Cancelled`, and the SP-004 guarded `ShutdownAsync` drains with a bound. No WPF shape survives: fire-and-forget sites (`ChatInput.cs:652,663`; `KeywordTriggerService.cs:1304`; `LocalAiService.cs:586`; `App.xaml.cs:1475`) and dispose-only shutdown (`App.xaml.cs:3253`) are **REJECTED**.
2. **Placement (pre-approach consult correction):** panic is proven in **c1** at pipeline level (typed `Cancelled` + stale discard + bounded drain), re-verified in **c2** against a real in-flight network operation (SP-019 item 1 mid-stream-cancel shape, in-product: 0ms typed `Cancelled`, `client-gone` observed by the lab). c7 carries only the headed proof that the UI surface goes quiet on panic. Mapping in §8 says so explicitly.
3. **Timeout is never the cancellation mechanism** (contract §2 rule 1; SP-019 item 2): provider timeouts are failure classifiers; token-source disambiguation is by linked-CTS origin, not exception-type guessing.
